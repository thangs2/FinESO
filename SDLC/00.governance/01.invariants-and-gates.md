# SDLC Governance — Sacred Invariants & Acceptance Gates

This document defines the mandatory engineering standards for all work items, ensuring that no feature is merged if it violates financial discipline or the operational isolation of developer harness environments.

---

## 1. The Five Sacred Invariants

| Invariant Code | Name | Core Mandate | Mandatory Enforcement Mechanism |
| :--- | :--- | :--- | :--- |
| **INV-01** | **No Evidence $\to$ No Claim** | Every financial figure, metric, statement, or warning emitted to users must be anchored to at least one `evidence_item` with explicit cell coordinates (e.g. `Sheet1!D15`), voucher ID, or bank transaction row. | `createEvidenceItem` in `fineso-core` rejects issuance if source URI or coordinate is missing. |
| **INV-02** | **Deterministic Calculator vs Probabilistic LLM** | All arithmetic operations (addition, subtraction, multiplication, balance rollups, cost allocations, debt aging, cashflow projections) must be executed by **deterministic DuckDB / SQL / TypeScript functions**. LLMs are strictly forbidden from performing mental math in conversational context. | All calculations must originate from `fineso-adapters` and `fineso-decision`. |
| **INV-03** | **Deny Raw Excel Dump in Context** | Never load entire spreadsheets or CSV files with thousands of rows directly into the LLM context window to prevent token explosion and line hallucination (Token-Diet discipline). | Use DuckDB to query slices and emit compact JSON recordsets. |
| **INV-04** | **Rubric Gate $\ge 85/100$** | Financial reports are only released when the Evidence-Sufficiency Score reaches $85/100$ or higher. If audit data is incomplete, the system triggers Fast Fail-Closed, terminates evaluation, and requests supplemental vouchers. | `Automated Rubric Validator` in `fineso-core` executes prior to any executive presentation. |
| **INV-05** | **Dual-Harness Isolation (Cursor vs Antigravity)** | `.cursor/` is an isolated workspace environment strictly reserved for **Cursor IDE** (`.mdc` rules). `.agents/` is an isolated workspace environment strictly reserved for **Google Antigravity IDE** (`.md` rules). Strictly FORBIDDEN to delete, merge, or cross-migrate files between these trees. | Harness hook verifies folder integrity and rejects commits upon detecting cross-contamination. |

## 2. Definition of Ready (DoR)

A task or story is eligible to enter the active implementation state only when it satisfies the **Purpose & Clarity** block:
- **P-01 (Purpose)**: Defines the real-world business and financial pain point solved for the enterprise.
- **P-02 (Objective)**: States measurable, automatically verifiable system behavior.
- **P-03 (Serves)**: Identifies the primary beneficiary (Business Owner, Finance Manager FM, or core infrastructure package).
- **P-04 (Expects)**: Specifies input data sources (Excel file path, config parameters, data schemas).
- **P-05 (Produces)**: Delivers fully packaged, production-ready runnable code; purely theoretical documentation is rejected.
- **P-06 (Code vs Documents)**: Strictly separates runtime executable logic from descriptive user documentation.
- **P-07 (Risk if wrong)**: Evaluates business consequences if calculation is inaccurate (e.g., liquidity dry-up, tax audit penalty).
- **P-08 (JEV Gating & Points)**: Explicitly identifies the TypeSafe JEV System 1 intervention touchpoint (from the 9 touchpoints) and its safety gating policy (`allow/ask/deny`).

## 3. Definition of Done (DoD)

A technical task is considered complete only when:
1. **Automated Testing**: 100% of unit tests executed via `bun test` pass cleanly.
2. **Code Coverage Gate**: Minimum $\ge 80\%$ test coverage on core mathematical and gating logic.
3. **Type & Lint Safety**: Zero lint warnings (`bun run lint`) and zero TypeScript compiler errors (`tsc --noEmit`).
4. **Evidence Preservation**: Computation output transforms directly into an `EvidencePack` achieving Rubric Gate $\ge 85/100$.
5. **JEV Gating & Decision Ledger Audit**: Sensitive financial decisions must pass TypeSafe JEV gating and be hashed with SHA-256 into `.harness/harness.db`.
6. **Dual-Harness Compliance**: Ensures zero modifications or file deletions that degrade the isolation of `.cursor/` and `.agents/`.
